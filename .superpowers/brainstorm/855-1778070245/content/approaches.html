三种方案对比

目标：动态步行 10-80 cm/s，95%+ 不摔倒，姿态稳定。最小改动，不过度设计。

A

纯参数调优

不动 C++ 代码，只通过前端/EnvConfig 调参

改动

  • HeightRewardScale 0.08 → 0.25
  • AliveReward 0.1 → 0.06
  • HeightDropPenaltyScale 0.5 → 1.5
  • BodyHeightRewardMax → 实际站高
  • BodyHeightThreshold 45 → 60
  • TrunkTiltPenaltyScale 0.05 → 0.15
  • 站立阶段延长到 300K 步

风险

  • 膝关节弯曲问题无直接信号
  • 网络可能找到其他作弊策略
  • 参数耦合度高，调参空间大

代码改动：0 行 C++。风险最低但可能治标不治本。

B

最小奖励手术 ★ 推荐

新增 2 个奖励分量 + 参数调整

改动

  • 新增：膝关节伸展奖励 — 膝盖越直奖励越高，直接对抗蹲姿
  • 新增：倾倒预警 — 倾斜超过阈值50%时线性预警
  • Height 惩罚区下边界提升 (85%→90%)
  • Alive 倾斜门控：uprightDot < 0.7 时 Alive=0
  • 全部参数调整（同方案A）

风险

  • 2 个新 UPROPERTY 加入 EnvConfigLoader 白名单
  • 观测空间不变，无需重新设计网络

代码改动：~30 行 C++，2 个新参数。用最小代价直击要害。

C

CoM + 姿态重设计

新增观测维度 + 多分量重构

改动

  • 观测空间 +4：膝关节角度 (左/右) + CoM 投影 XY
  • 奖励重构：以 CoM 稳定性为核心的评估体系
  • 新增重心投影惩罚、ZMP 近似约束
  • 全部方案B内容也包含

风险

  • 观测维度变化 → 网络需要重新训练
  • CoM/ZMP 计算增加每帧开销
  • 改动量大，调试周期长
  • 违反 "不过度设计" 原则

代码改动：~100 行 C++，5+ 新参数。理论最完备但工程成本最高。
